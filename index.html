¿Qué es el testing?

Método para verificar que el software cumple los requisitos esperados, ejecutándolo con herramientas manuales o automáticas, para tener la menor cantidad de errores posible.

  • Importancia: errores detectados temprano se resuelven antes de entregar → confiabilidad y satisfacción del cliente.
  • Beneficio: evita pérdidas de dinero (o humanas), desprestigio, y ahorra costos a largo plazo.

Funcionales

"Hace lo que debe hacer". Unitarias, integración, aceptación…

No funcionales

Rendimiento, seguridad, usabilidad. "¿Cumple lo esperado?"

Mantenimiento

Cuando el software ya está publicado.

Verificación vs Validación

Verificación: ¿construimos el producto correctamente según las especificaciones? (durante el desarrollo)

Validación: ¿construimos el producto correcto? Resuelve el problema del usuario en un entorno real.

Habilidades del QA

Blandascuriosidad, atención al detalle, analíticas, comunicación, organización, trabajo en equipo, perseverancia, metodologías ágiles (Kanban/Scrum).

Técnicasbases de datos, gestión de pruebas (JIRA, TestLink, Notion, Bugzilla), APIs (Postman, Swagger), programación (JS, Python, Java).

7 principios del testing

  1. Pruebas exhaustivas imposibles: se prioriza según riesgo.
  2. Agrupación de defectos: Pareto, 80% de errores en 20% de módulos.
  3. Paradoja del pesticida: mismos tests = dejan de encontrar bugs; hay que renovarlos.
  4. Presencia, no ausencia: probar demuestra que hay defectos, nunca que no hay.
  5. Falacia de ausencia de error: sin errores pero sin cubrir la necesidad del usuario = fracaso.
  6. Pruebas tempranas: cuanto antes, más barato corregir.
  7. Dependen del contexto: cada tipo de sistema se prueba distinto.

Implementación (vértice de la V)

Idea clave: las pruebas se planifican desde el inicio, no al final.

⬛ Caja negra

Sin conocer el código. Entradas, salidas y requisitos. Lo más usado por testers funcionales.

Login: usuario juan, clave 1234 → ¿entra?

⬜ Caja blanca

Con el código: rutas, condiciones, bucles, cobertura. Lo hacen devs o testers que programan.

Edad=20 → permite; Edad=15 → rechaza (ambos caminos).

🔘 Caja gris

Conocimiento parcial de lo interno (BD, APIs) sin revisar todo el código.

Pago: verificar en tabla payments estado APPROVED y que no haya pedido duplicado.

Técnicas de caja negra

  • Partición de equivalencia: grupos de entradas equivalentes. Edad 18–60: 15 (inválido), 30 (válido), 70 (inválido).
  • Valores límite: 17, 18, 19, 59, 60, 61.
  • Tablas de decisión: varias condiciones/reglas de negocio (if / else if / else).
  • Transición de estados: cambios de estado correctos. Ej: si el usuario pagó, que se vea reflejado (pendiente → aprobado).
  • Casos de uso / escenarios: interacción real del usuario.

Técnicas de caja blanca

  • Cobertura de sentencias: cada instrucción se ejecuta ≥1 vez.
  • Cobertura de decisiones/ramas: cada decisión en verdadero y falso.
  • Cobertura de condiciones: cada condición lógica en V y F.
  • Pruebas de caminos: recorrer los caminos posibles.

Basadas en la experiencia

  • Exploratorias: se diseña y ejecuta a la vez (útil cuando no se conoce el software).
  • Error guessing: casos según errores comunes de proyectos similares.

Estático

Sin ejecutar: revisa requisitos, documentación, diseño, código. Revisiones, inspecciones, walkthroughs, análisis con herramientas. Detecta defectos temprano y baja costos.

Dinámico

Ejecutando el software y comparando resultado obtenido vs esperado. Unitarias, integración, sistema, aceptación, rendimiento.

Automatizadas (vs manuales)

Las ejecuta una herramienta o script (ej. Selenium) sin intervención humana en cada corrida.

Ventajas: rápidas y repetibles, ideales para regresión, menos error humano.

Desventajas: costo inicial, hay que mantener los scripts, no evalúan bien usabilidad.

Manual = una persona ejecuta y evalúa. Automatizada = un script ejecuta y compara.

Pruebas manuales

Ventajas: fáciles de empezar, detectan problemas de usabilidad, ideales para exploratorias y cambios frecuentes.

Desventajas: lentas si son repetitivas, errores humanos, caras a largo plazo.

Todo software se prueba manualmente antes de automatizarse; la automatización al 100% no es posible.

Niveles de prueba

  • Unitarias: funciones/métodos aislados, las hacen devs (JUnit, PyTest, NUnit, Mocha/Chai).
  • Integración: módulos juntos. Top-down: de lo principal (carrito y pago) a lo secundario. Bottom-up: de lo básico a lo principal.
  • Sistema: funcionalidad, interfaz, rendimiento, seguridad (diccionario, SQL injection), compatibilidad.
  • UAT: el cliente valida que cumple lo que necesita.

Documentación de testing

Plan de pruebas, casos de prueba, reportes de defectos, datos de prueba, reporte de evidencias, registro de ejecución, matriz de trazabilidad.

Plan de pruebas (el "mapa")

Responde: ¿qué probamos y qué no? ¿cuándo? ¿quién? ¿qué tipos? ¿ambiente y datos? ¿criterio de éxito? ¿riesgos? ¿cómo registramos resultados?

Secciones: objetivo, alcance, fuera del alcance, estrategia, tipos de prueba, ambiente, datos, roles, cronograma, criterios de entrada, riesgos, evidencias.

Buenas prácticas de un caso de prueba

  • Claridad: cualquiera puede ejecutarlo.
  • Atomicidad: un solo comportamiento.
  • Reutilizable: para regresión/automatización.
  • Trazable: ligado a un requerimiento (ej. RF-08).

Pasos en verbo infinitivo: Ingresar, Hacer clic, Seleccionar.

Cómo definirlo (5 pasos)

1 Identificar funcionalidad → 2 Escenario (feliz / negativo / borde) → 3 Precondiciones → 4 Pasos atómicos → 5 Resultado esperado claro.

Ejemplo del login (RF1–RF5): los 3 enfoques

  • Negra: correo+clave correctos → acceso; clave incorrecta → error; 3 fallos → bloqueo 15 min; clave de 6 caracteres → rechazada.
  • Blanca: ejecutar usuarioExiste+claveOK, usuarioExiste+claveMal, intentos<3, intentos≥3 y que se llame bloquearCuenta().
  • Gris: con 2 fallos verificar en la BD contador=2; al 3º estado "Bloqueada"; tras 15 min contador=0; login OK reinicia el contador.

Reporte de defectos

Permite que un dev entienda, reproduzca y corrija. "El login no funciona" es un mal reporte: faltan usuario, clave, esperado, obtenido, ambiente, pasos, frecuencia y evidencia.

Campos: ID, título, descripción, precondiciones, pasos, esperado, obtenido, ambiente, severidad, prioridad, evidencia, estado, caso relacionado.

Conceptos

  • Defecto: el sistema no cumple el comportamiento esperado.
  • Fallo: el problema se manifiesta al ejecutar.
  • Esperado ≠ Obtenido → posible defecto.

Estados de un defecto

Nuevo → Asignado → En desarrollo → Corregido → Listo para testing → Retest → Cerrado (si funciona) o Reabierto (si no).
